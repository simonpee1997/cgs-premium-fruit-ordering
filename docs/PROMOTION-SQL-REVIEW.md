# CHIPSTI promotion SQL review — review-only release v2

**Status: not approved for production execution or deployment.** All SQL execution described here used synthetic, isolated development databases. No production connection, migration, business-data change, Git push, Vercel publication or production backup was performed during this review. The latest review request supersedes the earlier publication approval.

## Scope and compatibility conclusion

Reviewed the complete earlier release (SHA-256 `34e7ee69b7ab78b2d9b38a19367678042894c352edbb762300731f2f26f048b2`) and every repository migration:

1. `001_core.sql`: business/branch identity, roles, RLS, stock, POS checkout, sales/payments/refunds, legacy percentage promotions, receipt sequence.
2. `002_voids.sql`: voids through existing refund accounting.
3. `003_metadata.sql`: `updated_at` columns, staff roles, historical sale category snapshots.
4. `004_online_store.sql`: online orders, stock holds, settings keyed by `branch_id`, staff payment confirmation, public catalogue and private server RPCs.
5. `005_product_english_names.sql`: English-name DML only; no price/stock/history changes.
6. `006_delivery_areas.sql`: exact postcode coverage, after-discount RM300 threshold, frozen shipping snapshots and configuration wrappers.
7. `007_payment_proofs.sql`: private receipts, server quotes, proof binding and mandatory manual verification.

**The corrected SQL is complete and passes PostgreSQL parsing, migration application and behavioral tests against a development reconstruction of 001–007. Exact compatibility with the current production Supabase schema is NOT yet confirmed.** No live schema export was supplied and production SQL was explicitly forbidden. A screenshot cannot establish whether an earlier query committed any changes.

The fresh-install bundle contains a fail-closed preflight for **33 tables / 261 required columns**, their types/nullability/RLS, **eight existing function definitions** (the five it replaces/renames plus three authentication helpers), the relevant **two RLS policies**, untrusted-schema CREATE privileges and business/branch identity. Whitespace-only differences in existing function bodies can cause a conservative rejection. Additional custom constraints, triggers or integrations still require comparison with a real schema-only export. The manifest is labelled as development-derived, not a production export.

The current design is one CHIPSTI business with branch-scoped coded offers. Products and legacy uncoded promotions were globally shared in the baseline. This release does not convert the entire POS into a multi-business platform. No separate invoice table exists in migrations 001–007; preservation checks cover sales, receipt/payment records, refunds and export-related data. Any production-only invoice integration must be reviewed from its actual schema.

## Campaign and money rules

- Code: `CGSVIP20`, case-insensitive and globally unique among coded offers.
- Name: Cili Gemuk Selayang Customer Special; main branch `20000000-0000-0000-0000-000000000001` in CHIPSTI business `10000000-0000-0000-0000-000000000001`.
- Discount: **2000 basis points = 20%** of eligible product subtotal, rounded once to integer sen. No shipping/tax discount, no minimum/cap/usage limit for this campaign, no stacking or customer-identity requirement.
- Starts 6 November 2026 00:00:00 MYT (`2026-11-05 16:00:00+00`). Last valid instant is 30 November 2026 23:59:59.999999 MYT (`2026-11-30 15:59:59.999999+00`). The next midnight is expired.
- RM200 products → RM40 discount → RM160 products before shipping/tax. RM350 → RM280: delivery fee applies. RM400 → RM320: free delivery only for an existing exact configured eligible postcode.
- Minimum spend/eligibility/exclusions/caps and optional manual stacking use one evaluator; stock, prices, final amount, tax and shipping are revalidated server-side. Per-item allocations add up exactly to the frozen order discount. Refunds use net sale values and preserve cumulative sen rounding.
- Redemption is reserved atomically when the order is accepted, while the code is published and valid. These unexpired holds consume quota alongside paid redemptions. A later campaign pause/expiry/edit blocks NEW redemptions; it does not reprice a previously accepted order. Such an existing order may still be manually paid within its original 24-hour hold. This preserves the customer's accepted amount, including customers who already transferred funds. An expired/released hold cannot be paid or reused. Refunds reduce reported net sales without restoring the consumed code slot.

## Permission and function review

- Anonymous customers cannot call promotion management, simulation, redemption reservation, server quote/placement or private implementation functions directly with the anon key. They use validated same-origin, rate-limited Next.js routes; only the server has service-role RPC access.
- Owner management requires an active profile, owner role, its own branch and CHIPSTI business. Managers/cashiers cannot manage offers; owner/manager payment confirmation keeps the existing branch/session/proof/verification checks.
- New tables have RLS. Authenticated users have no direct writes to revision/redemption tables; owner SELECT policies are branch scoped. New audit visibility is scoped without changing legacy audit rows.
- Private helpers and the renamed private implementations explicitly revoke EXECUTE from PUBLIC, anon, authenticated and service_role. The appropriate public wrappers grant only their intended roles. SECURITY DEFINER paths are fixed to `public,pg_temp`; the baseline already revokes untrusted CREATE on public and preflight checks this. No dynamic SQL is built from customer inputs.
- Tests simulate permissive Supabase default function/table grants and confirm the explicit revocations still hold. Service-role credentials remain trusted server credentials with bypass capabilities; never expose them to a browser or commit them.

## Tests and results

- `npm test`: **106 tests pass** in nine suites using isolated PGlite databases. Includes exact final-second/date boundaries, every non-redeemable status, spoofed prices/categories/status/time, invalid quantities, branch/business separation, RLS/privileges under Supabase-style defaults, frozen historical rows, old pending orders, old POS promotions, discounted tax/refunds, immutable ledger and missing-payment rejection.
- `tests/postgres-promotion-review.mjs`: **15 checks pass** using isolated native PostgreSQL 18 and independent clients. Covers separate draft/publication, native permissions, true final-slot contention, duplicate retries, valid discounted payment settlement, legacy POS pricing, expiry/pause/start-time lock races, late confirmation, proof expiry, full atomic rollback, function/column drift rejection, wrong-business rejection and reproduction of truncated-function SQLSTATE 42601. These are development fixtures, not actual merchant payments.
- `npm run lint`, `npm run typecheck`, `npm run build`: pass locally.
- `npm run test:browser`: **81 tests pass** across desktop, tablet and mobile using intercepted fixture APIs. These cover UI/contract behavior; the SQL integration checks above validate the real database logic separately.
- The complete bundle's named dollar quotes are paired, and PostgreSQL creates/validates every function and SQL block. Late injected failure is rolled back and the original schema passes the baseline preflight again.

Managed Supabase auth/Storage APIs are simulated by the isolated test bootstrap; hosted JWT/session behavior and Storage service integration were not reverified against production.

Not performed: any live schema inspection, production migration, backup/restore, deployment, real customer checkout or merchant settlement. A development rollback test is not evidence of a working production backup.
